# Key files — differ navigation

`src/differ/navigation/`: dive-in and back navigation — call activities, decisions, handlers, correlations. Overview, flows and scopes — [`../architecture.md`](../architecture.md).

| File | Purpose |
|------|-----------|
| `process-file-index.js` | `ProcessFileIndex` — the processId→file index (a walk of the whole repository tree + a cache in localStorage + deep XML parsing). Now used only as a **fallback** in `CallActivityLocator`; to be removed once blob-search proves reliable |
| `call-activity-locator.js` | `CallActivityLocator` — resolves processId→{filePath,fileName} for "drilling into" a Call Activity. Primary path: a pinpoint GitLab blob-search by `<bpmn:process id="...">` (only the needed file is loaded, an in-memory cache by ref+processId); fallback — `ProcessFileIndex`. `blobSearchPageUrl` — a link to the GitLab search if the file is not found. Mirrors `handler-locator.js` |
| `caller-locator.js` | `CallerLocator` — the reverse of `CallActivityLocator`: resolves the diagram's own process id(s) → the BPMN files that **call** it (a targeted blob-search for `calledElement="<processId>"` — `processId="<processId>"` under the C8 dialect, read through the injected dialect getter — unioned across ids, cached per ref+ids, current file excluded). For the back-navigation caller picker (FEAT-0023). `resolveCallers` returns `[]` for a root diagram but **throws** on a failed search, so the UI distinguishes "no callers" from "couldn't check". `selectCallers` (pure) is unit-tested |
| `back-navigator.js` | `BackNavigator` — the toolbar "dive out" control (FEAT-0023, now mounted on **both** the BPMN and DMN differ — FEAT-0005), the mirror of the dive-in `⤵`: a split `⤴`/`▾` button that moves UP the call hierarchy to a calling diagram (it lands on "where we came from" only when we got here by diving in — a coincidence, not the definition). `⤴`: when we dived in, the caller's tab is open above us, so jump straight to it (the injected `onDiveOutToOpener` focuses it — instant, state-preserved); otherwise open the menu. `▾` opens a lazy dropdown of all diagrams that call this one (via `CallerLocator`), the one we dived in from marked and listed first (selecting it reuses its open tab); the rest open fresh (`onOpenCaller`, which auto-selects their call site). Distinct loading/empty/error states. Owns only its DOM; `createElement()` returns null when there is nothing to offer. Unit-tested in jsdom |
| `call-activity-navigator.js` | `CallActivityNavigator` — a minimalist "⤵" overlay on the selected Call Activity (styled like `handler-link`, with a title tooltip). On click it resolves the file via `CallActivityLocator` against the displayed version (`#getShownRef`) and opens its differ; if not found — it opens the GitLab search. The called id comes from `calledProcessId(bo, dialect)`; a FEEL id (`=…`) goes straight to the search page, unsearched. During resolution (`#isHandling`) the arrow badge turns into a `.differ-spinner-inline` spinner and returns to an arrow on completion (UX-0008); the badge of any Call Activity selected during an unfinished resolution is also shown as a spinner (`#refreshBadge`) |
| `decision-locator.js` | `DecisionLocator` — the DMN mirror of `CallActivityLocator` (FEAT-0005): resolves a `camunda:decisionRef` → the `.dmn` file declaring it, by a targeted blob-search for `decision id="..."` (no `ProcessFileIndex` fallback). `selectDecisionFile`/`isDmnFile`/`blobSearchPageUrl`, cached per ref+decisionId |
| `decision-navigator.js` | `DecisionNavigator` — the DMN mirror of `CallActivityNavigator` (FEAT-0005): the "⤵" dive-in overlay on a selected `bpmn:BusinessRuleTask` with a `decisionRef`, reusing the `.dive-in-call-activity` badge. On click resolves the file via `DecisionLocator` and opens its DMN differ (the differ kind is chosen by extension in `DifferTabNavigator`); not found / a `${…}` expression → GitLab search; the id is `calledDecisionId(bo, dialect)` (C8: `zeebe:calledDecision`), a FEEL id (`=…`) → the search page without a search |
| `decision-caller-locator.js` | `DecisionCallerLocator` — the DMN mirror of `CallerLocator` (FEAT-0005): resolves this decision's id(s) → the BPMN files whose `bpmn:BusinessRuleTask` calls it (blob-search `decisionRef="<id>"`, `decisionId="<id>"` under C8 — the DMN differ detects the dialect from its loaded XML —, current file excluded, unioned, cached per ref+ids). Powers the DMN differ's back-navigation; `resolveCallers` returns `[]` for a top-level decision but **throws** on a failed search. `selectCallers` (pure) is unit-tested |
| `handler-locator.js` | `HandlerLocator` — links a service task to the handler code by a **namespaced key** `topic:<topic>` (external task) \| `class:<SimpleName>` (delegate): `findChangedHandlers` (scans the changed `.kt`/`.java` from the MR changes API → `Map<key, {filePath, diffType}>`, where `diffType` = `added`/`changed`/`removed`; deleted files are scanned on the target-ref, the rest — on the mr-ref) and `resolveLocation(key, ref)` (a dispatcher by prefix → GitLab blob-search → file:line). External task: the annotation names are configurable (FEAT-0035, `core/handler-annotations.js`) in two styles — a **topic** annotation states it explicitly (`@ExternalTaskSubscription("<topic>")`, `@JobWorker(type = "<job type>")` — both on by default) and a **class-name** annotation states nothing, the topic being the class name with the first letter lowercased (opt-in, no stock Camunda annotation works this way). With no class-name annotation configured that search path is skipped entirely. Delegate: `camunda:class="com.foo.Bar"` → `class:Bar`; `camunda:delegateExpression="${bar}"` → bean → `class:Bar` (resolution — a search for `class <Name>` in the handler file). Matching is by simple name (not FQN) → package collisions are possible; limitations (a non-standard bean, a complex expression, transitive analysis — [FEAT-0015]) — in the file header. Camunda 8 (FEAT-0038): `handlerKeyFromBusinessObject(bo, dialect)` reads, under the C8 dialect, the job type of the `zeebe:TaskDefinition` in the element's own `extensionElements` (also on a message throw/end event) → `topic:<type>`, with no key for Camunda's connectors (`io.camunda:…`) or a FEEL type; the C7 reading is unchanged and the two never fall back to each other. One parser serves every configured topic annotation: the topic is a string literal that is positional or named `type`/`value`/`topicName` at any position (other named strings ignored, multi-line allowed); with no topic argument and a method declaration next, the method name (`@JobWorker fun screenFraud(` → `screenFraud`); a non-literal topic argument (a constant) or a class next → nothing. The same parser places the badge link on the annotation line (or the method line). `matchesExactTopic` counts `-` and `.` as part of a name, so a kebab-case prefix (`find-items`) never matches a longer job type (`find-items-in-catalog`) |
| `handler-navigator.js` | `HandlerNavigator` — a "‹/›" overlay badge on a service task: permanent for tasks whose handler is affected in the MR, colored by `diffType` (green=added, blue=changed, red=removed — like the diff colors; added is visible in the MR version, removed — in the target version, changed — in both), on click (neutral) for the rest. `#getHandlerKey(elem)` builds the namespaced key from the BO (external task / `camunda:class` / `camunda:delegateExpression`; a C8 job type through the injected dialect getter). Click: for an affected handler — open its diff in this MR, navigating the source MR tab (`window.opener`) and switching to it via `window.open(url, name)` using the opener's temporary `window.name` (more reliable than `opener.focus()`; fallback — a new tab); for the rest — the code at the currently displayed version in a new tab. A "handler" = an external task handler or a delegate (`camunda:class`/`delegateExpression`) |
| `correlation-locator.js` | `CorrelationLocator` (FEAT-0027) — finds where a message-catching element (`bpmn:ReceiveTask`, message catch/start/boundary event) is woken up in code, by the message **name** (correlation is keyed by name, not id). `extractMessageName(bo)` reads the name (ReceiveTask `messageRef`, event nested `MessageEventDefinition.messageRef`), flagging a `${…}` name as dynamic and excluding throw/end (sending) events. `resolveCorrelations(name, ref)` runs a two-phase GitLab blob-search (cached per ref+name; `per_page=100`). **Exact-term gate:** GitLab Advanced Search tokenises an underscored name (`FINISH_VERIFICATION_API`→`finish`/`verification`/`api`) and quoting is impossible (BUG-0013), so `collectHits` keeps only hits whose snippet literally contains the searched term — otherwise a handler correlating a *different* message is mis-taken for ours. Phase 1 searches the literal and classifies each hit (`correlation` keyword line / `constant` declaration `FOO = "<name>"` / `config` `.yml`,`.properties` / `diagram` `.bpmn`,`.dmn` excluded / `other`). **Phase 2 (case B) resolves a captured constant by fetching its *declaring file* and locating the correlation usage there (`findConstantCorrelationLine`, word-boundary match) — NOT a global search for the constant name:** message constants are routinely named generically (`CORRELATION_MESSAGE`), and a global search floods the result with OTHER messages' correlations (the companion-object idiom keeps declaration + usage in one file). Returns grouped, ranked hits `{ correlation, other, config, tests }`; **test hits (unit + auto-test, any language: `isTestPath` covers `/test(s)/`,`autotests/`,`e2e/` dirs, `*.spec.ts`/`*.test.ts`, JVM `*Test`/`*Spec`/`*IT` classes) are segregated into `tests` and hidden by default** (a future setting may opt them in). The pure orchestrator `resolveWith(name, searchFn, fetchFileFn)` is unit-tested with fakes. Mirrors `handler-locator.js` |
| `correlation-navigator.js` | `CorrelationNavigator` (FEAT-0027) — a "✉→" overlay badge (styled like `handler-link`) on a selected message-catching element. The search runs **lazily on click**, not on `selection.changed`; the badge becomes a `.differ-spinner-inline` spinner while resolving. Display policy: **a single result opens straight away** in a new tab (`blobFileUrl`), no dropdown — whether it is an exact correlation point or the one weaker lead found. Several results → a flat-list dropdown (no group headers): the correlation points if any, else the weaker leads (constant declaration / config), shown plainly. The dropdown mirrors `back-navigator`'s menu (anchored to the badge, close-on-outside-click). A dynamic name → an explanatory note + any config hits; failed search / only-test matches / nothing → a short message (no GitLab-search link — it 404s on this instance) |
