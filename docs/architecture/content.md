# Key files — content scope

`src/content/`: the entry point, `App`, the GitLab and GitHub repo/UI providers. Overview, flows and scopes — [`../architecture.md`](../architecture.md).

| File | Purpose |
|------|-----------|
| `main.js` | Entry point (async): decides GitLab or GitHub (`detectPlatformKind`), skips non-HTML documents (raw, JSON), and only then initializes App. An unrecognised site runs nothing and, unless the page is an error response (navigation status ≥ 400 — GitLab's own 404/5xx pages carry no GitLab markup), is recorded in `chrome.storage.local` `undetectedSites` (`reportUndetectedSite`); a recognised page clears its entry without delaying the app's start. The service worker prunes the list to granted hosts and shows `!` while any is pending |
| `app.js` | Main application class, orchestration |
| `gitlab-repo-provider-base.js` | `GitLabRepoProviderBase` — the shared base of both GitLab providers (keeper): `isAvailable`, `init` (+ project id resolution with a cache), `getProjectInfo`/`getChangeInfo`, `isChangeViewActive`, `getBranchFileType`, `extractBranchCommitIdAndFilePath` (async: the page's ref hint, or — when the page states none — the URL-tail prefixes probed shortest-first against `GET /repository/commits/:ref`, cached by URL; BUG-0035), `getTargetFilePath` (resolves `old_path` for a renamed file via the MR `/changes` API + the static `extractRenameMap`, cached by URL; no iid / no rename / error → `filePath`, BUG-0002). The collaborators `urlParser`/`domScraper` are ordinary fields (for subclass access); `loadContent` is injected (DI for tests, defaults to `loadFileContent`) |
| `gitlab-repo-provider.js` | `GitLabRepoProvider` — the DOM/heuristic path on top of the base (fallback, "doomed" per REFAC-0001): `initChangeInfo` (MR info from the API URL + cache), `getChangeBranchNames` (via the scraper), `getSourceCommitId` (commits.json → `diff_head_sha`), `getTargetCommitId` (delegates to `MergedMrCommitResolver`) |
| `gitlab-url-parser.js` | `GitLabUrlParser` — pure URL/path parsing (no DOM/network): `parseProject`, `extractMrIid`, `buildMrApiUrl`, `isMrDiffPage`, `getBranchFileType`, `extractBranchCommitIdAndFilePath`, `blobRefCandidates` |
| `gitlab-dom-scraper.js` | `GitLabDomScraper` — all DOM reads of the GitLab page (the most fragile part): `findBranchCommitIdText` (the two older ref-selector markups, then gitlab.com's `#js-ambiguous-ref-modal[data-ref]`), `getMergeRequestBranchNames`, `findDiffHeadSha`, `isMergedByBadge`. MR file blocks are not read here — they are button hosts, owned by `GitLabUIRepoProvider` |
| `merged-mr-commit-resolver.js` | `MergedMrCommitResolver` — a heuristic for resolving the target commit of a merged MR (the DOM path's role; "doomed"): `resolveTargetCommitId` (branching merged/opened, cache) on top of `MasterCommitManager` and the atom feed of master commits filtered by title |
| `single-entry-cache.js` | `SingleEntryCache` — a generic "last value per key" cache (init/MR-info/target-commit/filteredByTitle) |
| `gitlab-ui-repo-provider.js` | Button injection. MR: `syncFileButtons(describeFile)` keeps one `.bpmn-surf-file-btn` per diagram block — rapid diffs `<diff-file>` (path from `data-file-data`) and legacy `.diff-file.file-holder[data-path]` — before the ⋮ menu of the block's actions (`.rd-diff-file-info` / the header's `.file-actions`); idempotent (no DOM mutation when every block is served), replaces a button whose path differs from its block's; `removeFileButtons()` before a rebuild. Branch view: `addButton` puts a split button first in the blob header's `.file-actions` (beside GitLab's groups, not inside the viewer switcher); its caret menu holds "Diff with local file…" (UX-0010), closed on outside mousedown/Escape, listeners torn down in `reset()`. Labels (UX-0009): `Schema diff`/`Decision diff`, `View schema`/`View decision`; accent `.bpmn-surf-btn-accent` (redefines GitLab's `--gl-button-default-primary-*` variables, since GitLab's button rules outrank a single class) + the inlined bpmn-surf icon; styles and the rapid-diffs grey-out rule in `content/content-styles.css` |
| `repo-provider.js` / `ui-repo-provider.js` | The base provider interfaces. The `RepoProvider` method names are platform-neutral (`isChangeViewActive`, `initChangeInfo`, `getChangeInfo`, `getChangeBranchNames`, `getSourceCommitId`, `getTargetCommitId`, `getDiffSideLabels`, `getTargetFilePath`) — the core is not tied to GitLab/MR. `getTargetFilePath(filePath)` by default returns `filePath` (identity), differs only on a rename (BUG-0002); resolved lazily in `app.js#openDiffer` on click (outside the `mouseup` hot path), `FallbackRepoProvider` delegates to the active provider. `getDiffSideLabels(sourceRef, targetRef)` returns human-readable side labels (`{sourceLabel, targetLabel}`): the provider itself decides whether these are branch names (the whole-MR diff) or a commit message + short id (a single commit selected), and only the ready strings go to the differ; it may be async (if commit metadata needs to be requested). `UIRepoProvider` also holds what both platforms' buttons share: the label texts (`buttonText`: `Schema diff`/`Decision diff`, `View schema`/`View decision`), the icon and chevron SVG, and the "Diff with local file…" split-button menu (`buildLocalFileMenu`, `toggleMenu`, `closeMenu`, `readLocalFile`) |
| `repo-provider-factory.js` | `createRepoProvider`/`createUIRepoProvider` — the single place that knows about the concrete implementations and their order; the wiring point for new platforms/REFAC-0001. `createRepoProvider` chains `[GitLabApiRepoProvider, GitLabRepoProvider, GitHubRepoProvider, GitHubApiRepoProvider]` (the GitHub pair is available only for the `github` kind); `createUIRepoProvider` detects the kind once via `detectPlatformKind()` and returns the first UI provider whose `isAvailable(kind)` is true, throwing if none matches (rather than guessing a provider that could not work). Neither factory hardcodes a host→provider mapping — each provider answers for itself |
| `platform-detection.js` | `detectPlatformKind(location, doc)` + the `PLATFORM_KIND` constant (`GITLAB`/`GITHUB`) — the single source of truth for "which platform is this page?" and for the `platform.kind` vocabulary in the content scope (REFAC-0004 step 1.4). Order: `github.com` / `gitlab.com` by name → the user's per-site choice (`setSiteKindOverride`, from `settings.siteKinds`) → the page markup (`og:site_name` starting with "GitHub" or `meta[name=expected-hostname]` → github; `og:site_name=GitLab` or `body[data-page]` → gitlab) → `null` (unknown: nothing runs, the user is asked in the popup). (`reportUndetectedSite`/`clearUndetectedSite`, which keep `chrome.storage.local` `undetectedSites`, live in `core/settings.js`.) The detected kind is computed once at the selection site (`FallbackRepoProvider`, `createUIRepoProvider`) and **passed into** each provider's `isAvailable(platformKind)`; also feeds `diff-params-builder.js#platform().kind`. |
| `fallback-repo-provider.js` | `FallbackRepoProvider` — a whole-provider fallback: on `init()` it picks the first available and successfully initialized implementation from the ordered list, then delegates all interface calls to it |
| `gitlab-api-repo-provider.js` | `GitLabApiRepoProvider` — resolves MR parameters via the GitLab MR API (`GET /api/v4/projects/{id}/merge_requests/{iid}`, a single cached request). `extends GitLabRepoProviderBase`: implements commit/branch/title resolution (`getSourceCommitId`←`diff_refs.head_sha`, `getTargetCommitId`←`diff_refs.base_sha` — uniformly for opened/merged; `getChangeBranchNames`←`source_branch`/`target_branch`), and inherits the DOM/URL detection methods (file selection, branch-view, project id) from the base. When a single commit is selected (`?commit_id=`), `getTargetCommitId` returns the commit's parent (FEAT-0001), and `getDiffSideLabels` labels both sides with the commit message + short id (from the commits API, cached by sha) instead of branch names — otherwise the target would be labeled with the target branch, which is incorrect. First in the chain (primary); on an MR page `init()` tries the API and, on a missing `diff_refs`/error, returns `false` → `FallbackRepoProvider` falls back to the DOM `GitLabRepoProvider`. There is no per-method fallback |
| `diff-params-builder.js` | `DiffParamsBuilder` — assembles the differ page's neutral parameters (sourceRef/sourceLabel/targetRef/targetLabel/changeRequestId) + a `platform` descriptor `{kind,projectUrl,hostUrl,projectId}`; `sourceLabel`/`targetLabel` are the ready side labels from `getDiffSideLabels` (a branch name or a commit message + short id); the platform specifics are grouped under `platform`, discriminated by `kind` |
| `github-repo-provider-base.js` / `github-repo-provider.js` / `github-api-repo-provider.js` | `GitHubRepoProviderBase` implements every `RepoProvider` method over a `this.pull` that subclasses fill in via `resolvePull()`; `init()` returns false whenever the pull is unresolved (a true with null refs would make `App` reload the page). `GitHubRepoProvider` (primary) reads the refs from the PR page (`GitHubDomScraper.pullRefs`, re-fetching the page once per path — `/changes` or `/changes/<range>` — when a soft navigation or a commit-picker switch left a stale payload; a large PR's page embeds no file diffs, so one file's diff comes from GitHub's own same-origin `page_data/diff_entries`, cached per PR) and renamed paths from the rendered file blocks — no API request. `GitHubApiRepoProvider` (fallback) uses the anonymous REST API (`pulls/{n}` + `compare/{base}...{head}`, cached per PR for the page's lifetime) and only once the page has rendered file blocks, so a still-loading page never spends quota |
| `github-url-parser.js` | `GitHubUrlParser` — pure URL parsing: `parsePullFiles` → `{owner, repo, number, range}` (`/pull/{n}/files|changes`, optionally `/<sha>`, `/<a>..<b>`, `/BASE..<b>`, and `/pull/{n}/commits/<sha>`; the Conversation tab stays silent), `apiBase(hostUrl)` (REST base: `api.github.com` or `{host}/api/v3`), `parseBlob`, `getBranchFileType`, `splitRefAndPath` (a ref with a slash is resolved against the page's own ref), `pullApiUrl`, `compareApiUrl` |
| `github-dom-scraper.js` | `GitHubDomScraper` — all DOM reads of the GitHub page, for both "Files changed" UIs (classic server-rendered `div.file-header[data-path]`, and the React UI that virtualises its blocks): `fileBlocks(doc)` → `{path, oldPath, actions, before}[]`, `pullRefs(doc, number, entries, range)` (classic: the `sha1`/`sha2` of the diff loader or the `show_toc` menu, and for a selection only when `sha2` is the URL's end and, for `<a>..<b>`, `sha1` its start; new UI: the embedded payload — the shown pair `diffContents[].oldCommitOid/newCommitOid`, never `comparison.baseOid`, which is the base tip; the page keeps its first payload across commit-picker clicks, so a payload is read only when it shows the URL's selection: whole PR → `viewing` FULL, one commit → `viewing` COMMIT of that commit, a range → its pair, by SHAs not by `viewing` (a range spanning one commit is viewed as COMMIT; `BASE..x` starts outside the PR's commits); a selection is labelled `<headline> (<shortSha>)`, the base branch or the short SHA; `lazyDiffEntry(doc, number, range)` → `{path, range}` names the file and the `page_data/diff_entries` range to load when a large PR embeds no diffs — the URL's range, a commit as parent..commit, the whole PR as its head — and `pullRefs(doc, number, entries, range)` checks and reads the loaded ones), `findBlobRef`, `blobActionsAnchor` |
| `github-ui-repo-provider.js` | `GitHubUIRepoProvider` — button injection on GitHub: `syncFileButtons` puts one `Schema diff`/`Decision diff` button in every diagram file's header (first in the classic actions row, before "More options" in the new UI; blocks come and go as the new UI virtualises them); `addButton` puts the `View …` split button with the local-file menu before the Raw group on a blob page. Own classes only (`bpmn-surf-gh-*`, `content-styles.css`, with GitHub dark mode) — no GitHub class is borrowed, so a GitHub restyle cannot break them |
| `file-type-detector.js` | Determining the file type by extension |
| `camunda-bpmn-moddle-manager.js` | Loading/caching one moddle descriptor; `App` keeps one instance for `camunda.json` and one for `zeebe.json` (both warmed in `#resolveChangeView`, both sent as `camundaBpmnModdle` / `zeebeBpmnModdle`) |
| `master-commit-manager.js` | The MR target-branch commit history with a cache in localStorage (per project and branch) |
| `page-reloader.js` | Protection against reloads (max 3 attempts) |
