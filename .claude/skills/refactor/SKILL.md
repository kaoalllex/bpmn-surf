# Refactoring

## Allowed
- Improve structure, naming, separation of concerns
- Extract classes from flat code (following the pattern: differ-page class files, `master-commit-manager.js`)
- Reduce duplication, simplify logic
- Small, focused improvements

## Requirements
- Behavior is preserved **exactly**; the public UI and the user flow do not change. Preserve even observable trivia (log texts, typos in the UI) — fixing those is discussed separately
- One concern per change; small diffs; do not mix with features
- ⚠️ Global variables and functions are visible between scripts of the same scope. The scopes and their load order are in `docs/architecture.md` ("Three script scopes"). Before renaming/moving, find ALL usages across all js files
- ⚠️ The shared differ-page classes (`src/differ/shared/`) are used by both `bpmn-differ.js` and `dmn-differ.js` — when changing their API, fix both consumers. There must be no global mutable state on the differ page — state lives only in class fields
- `libs/` (generated by `npm run sync:libs`) and the `src/hosts/content-scripts.json` order — do not touch. Adding a file to `web_accessible_resources` and `utils.js#loadScripts` is a normal step when extracting code into a new file (`npm test` checks the registries stay in sync)
- A new differ-page file = an entry in `utils.js#loadScripts` (before `bpmn-differ.js`) + in the manifest's `web_accessible_resources`. Top-level `let`/`const`/`class` must not conflict with names in other scripts of the scope (redeclaration = SyntaxError); static class fields must not reference globals declared in later-loaded files

## Workflow
If a spec/plan for this task already exists in `docs/superpowers/` (from `brainstorming`/`writing-plans`), it covers steps 1–3: start at step 4.

1. Explain what to refactor and why, describe the trade-offs
2. Propose a plan with files and changes; key forks (file structure, scope) — via questions to the user
3. Wait for confirmation before structural changes
4. Apply incrementally
5. Verify that behavior has not changed

## Post-refactoring check
1. `npm test` green — it also parses every `src/` script and checks the registries; the tests pin the current behavior, so a test failing during a refactor means a behavior change
2. Search for removed/renamed names across ALL js files — no dangling references (especially from `dmn-differ.js`)
3. Run the `code-reviewer` subagent with emphasis on a line-by-line comparison against the old version (`git show HEAD:<file>`)
4. Update the instructions per `docs/conventions.md` ("update the instructions" rule): `docs/architecture.md` and the area file in `docs/architecture/`, CLAUDE.md, `.claude/`
5. Remind the user of the manual checklist from `docs/testing.md` (including DMN diff — the shared differ-page classes)
6. If the refactor relates to a task in `docs/issues/` — update its file per `docs/issues/README.md`

If behavior might change: stop, explain the risk, request confirmation. Avoid overengineering — simplicity > abstraction.
