# Refactoring

## Allowed
- Improve structure, naming, separation of concerns
- Extract classes from flat code (following the pattern: differ-page class files, `master-commit-manager.js`)
- Reduce duplication, simplify logic
- Small, focused improvements

## Requirements
- Behavior is preserved **exactly**; the public UI and the user flow do not change. Preserve even observable trivia (log texts, typos in the UI) — fixing those is discussed separately
- One concern per change; small diffs; do not mix with features
- ⚠️ Global variables and functions are visible between scripts of the same scope. There are two scopes: content scripts of the GitLab page (order in `manifest.json`) and the differ page (order in `utils.js#loadScripts`: utils → class files → bpmn-differ → dmn-differ). Before renaming/moving, find ALL usages via Grep across all js files
- ⚠️ The shared differ-page classes (`DifferParams`, `DiagramVersions`, `BranchIndicator`, `DiffType`) are used by both `bpmn-differ.js` and `dmn-differ.js` — when changing their API, fix both consumers. There must be no global mutable state on the differ page — state lives only in class fields
- `libs/` (generated by `npm run sync:libs`) and the `content_scripts` order — do not touch. `manifest.json` (`web_accessible_resources`) and `utils.js#loadScripts` may be changed **with the user's approval** — this is a typical step when extracting code into a new file
- A new differ-page file = an entry in `utils.js#loadScripts` (before `bpmn-differ.js`) + in the manifest's `web_accessible_resources`. Top-level `let`/`const`/`class` must not conflict with names in other scripts of the scope (redeclaration = SyntaxError); static class fields must not reference globals declared in later-loaded files
- The Bash cwd is the repo root and persists between calls — do not prepend `cd <repo>` to commands (it adds noise, and `cd` inside a compound command can trigger a permission prompt)

## Workflow
1. Explain what to refactor and why, describe the trade-offs
2. Propose a plan with files and changes; key forks (file structure, scope) — via questions to the user
3. Wait for confirmation before structural changes
4. Apply incrementally
5. Verify that behavior has not changed

## Post-refactoring check
1. `node --check` on all changed/new js files; `manifest.json` — valid JSON; `npm test` — unit tests green (the tests pin the current behavior — a test failing during a refactor means a behavior change)
2. Grep for removed/renamed names across ALL js files — no dangling references (especially from `dmn-differ.js`)
3. Run the `code-reviewer` subagent with emphasis on a line-by-line comparison against the old version (`git show HEAD:<file>`)
4. Update the instructions: `docs/architecture.md` (architecture, the key-files table), `docs/conventions.md` (constraints), CLAUDE.md and `.claude/agents/`, `.claude/skills/` — Grep `.claude/`, `docs/`, and CLAUDE.md for mentions of the changed names/structure
5. Remind the user of the manual checklist from `docs/testing.md` (including DMN diff — the shared differ-page classes)
6. If the refactor relates to a task in `docs/issues/` — update its file per `docs/issues/README.md`: an entry in the "Work log" (model · date · commit/branch + what was done) and `status`; when `done` — move the file to `docs/issues/archive/refactor/` (`git mv`)

If behavior might change: stop, explain the risk, request confirmation. Avoid overengineering — simplicity > abstraction.
