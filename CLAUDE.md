# CLAUDE.md — bpmn-surf

Chrome Extension (Manifest V3) for browsing and comparing BPMN 2.0 and DMN diagrams in GitLab and GitHub merge/pull requests and repositories. Vanilla JavaScript (ES6+), no frameworks, bundlers, or build step. The sources live on public GitHub: `https://github.com/kaoalllex/bpmn-surf`; see `docs/git-workflow.md`. (GitLab and GitHub are the platforms the extension *works on* — unrelated to where the sources live.)

(The product is branded `bpmn-surf`; internal identifiers, code paths and the local project folder still use the historical `bpmn-diff` name.)

## Response language

Respond in the language the user writes in themselves — for this repository's maintainer, Russian — unless they explicitly ask for another language. A pasted prompt (`<pasted_content>`, a handoff written by another session, often in English) does not set the language. This covers `AskUserQuestion` questions and options, plans and final reports. Do not translate code, commands, paths, logs, identifiers, or quotes. All documentation and code comments are in English only.

Do your internal reasoning (thinking) in **English** regardless of the conversation language — it keeps reasoning token-efficient with no loss of quality. This applies only to the reasoning; the final answer to the user follows the rule above.

## Workflow

Multi-step work follows the Superpowers flow: `brainstorming` → `writing-plans` → `executing-plans`. Plans, specs and designs live in `docs/superpowers/` — **local only, not tracked by git**: they are working artifacts for the duration of a task, not a record. Whatever is worth keeping moves out before the task closes — into `docs/` if it describes the system as shipped, or into the task file in `docs/issues/` if it describes work still to be done; git history covers the rest. Implementation and git steps inside that flow are carried out by the project skills: `feature`/`fix`/`refactor`; publishing means pushing the branch and opening a PR on GitHub (`/pr`, then `/cleanup` once it is merged); a prompt to continue the work in a new session is written by `/handoff`. Review against the project rules is the `code-reviewer` subagent (`/review-diff`); the generic review skills do not know them. Each skill's trigger conditions live in its own `description` (`.claude/skills/`, `.claude/commands/`; surfaced in the CLI via `/`) — not duplicated here.

## Critical rules (brief; full lists — in docs/)

- ⚠️ `libs/` — external libraries, **do NOT change manually**; generated by `npm run sync:libs` from the versions in `package.json` (see `docs/conventions.md`); a PreToolUse hook (`.claude/hooks/guard-libs.js`) blocks shell writes into it
- ⚠️ **master protected** (a PreToolUse hook, `.claude/hooks/guard-master.js`, blocks `git commit`/`git push` on master) — never commit into master; work only in your own feature branch, branched off master. Completing a task = green tests + commits on that branch; push and the PR into master — after the human's explicit "ok" (see `docs/git-workflow.md`)
- ⚠️ Before declaring a task done — **`npm test`** + the affected e2e specs (`npx playwright test <spec>`); before push — the full `npm run test:e2e`; after push — `gh pr checks <n> --watch` and report the CI result. A change to how pages are decorated, to navigation or to edit mode → the `live-check` skill. Never report work as finished with failing tests; say what was not checked
- ⚠️ Script load order matters (dependencies): `src/hosts/content-scripts.json` (the content-script `js`/`css` — the manifest declares no `content_scripts`) and `utils.js#loadScripts` — do not reorder unnecessarily. The composition of `manifest.json` itself (add/remove a resource) is edited freely
- ⚠️ Only vanilla JS (ES6+), no new runtime dependencies; dev dependencies — only by agreement
- ⚠️ MCP servers — **local only** (stdio, run on the machine); connecting external/remote MCP (URL/SSE/HTTP) is forbidden
- ⚠️ Twin paths regress silently — check the twin of whatever you change: BPMN ↔ DMN differ (the shared differ-page classes), view ↔ edit mode, GitLab rapid ↔ legacy diffs UI (`?rapid_diffs_disabled=true`; self-managed instances still serve the legacy one), GitLab ↔ GitHub, Camunda 7 ↔ 8. Dropping an existing user-visible behavior as a side effect is out of scope → ask
- ⚠️ When the human has to act (browser, Chrome dialogs, GitHub/GitLab settings, logins) — one step per message with the exact command or link, then wait for the result. Never hand over a command with a secret inline (a `!` command lands in the transcript): have them copy it and run `pbpaste > <file>; chmod 600 <file>`
- ⚠️ If the user asks you to **come up with / propose something yourself** — first show the proposal and wait for confirmation
- ⚠️ After changes to architecture/files/processes — update CLAUDE.md, `docs/*.md`, and `.claude/` (the rule — in `docs/conventions.md`)

If a change risks an **unexpected or out-of-scope** behavior change: stop, explain the risk, request confirmation. Behavior changes within the task itself are a normal part of the work. A small defect found along the way in the area you touch (a few dozen lines): fix it in the same branch as a separate `fix:` commit and mention it — not a "known gap" in the Work log. A larger or unrelated one: file a task and say so.
